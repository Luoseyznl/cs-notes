# 管理文件系统

文件系统是将人类可读的文件与目录转换成硬盘上的 0 和 1 的“桥梁”，大多数 Linux 发行版在安装时就贴心地提供了默认文件系统，默认文件系统不一定是最适合你的，但一定是最通用的。

> Linux 的文件和目录以**虚拟目录树**的形式呈现，以虚拟文件系统 VFS 向上提供统一操作接口，向下支持多种物理文件系统（如 ext4、XFS、Btrfs 等）。VFS 还支持特殊的虚拟文件系统（如 procfs、sysfs），供用户空间程序访问内核数据结构和系统状态。

## 1. 基本文件系统

Linux 最初模仿 Unix 设计了 ext 文件系统（Extended File System）。其核心思想是将硬盘划分为固定大小的块（比如现代系统常见的 4KB 一个块），并通过索引节点（inode）系统来管理文件的元数据和数据块位置。

> Linux 最早期使用的是一个叫 MINIX 的简陋文件系统。由于 MINIX 限制极多（例如文件名最长仅支持 14 个字符），开发者重新设计了 ext 文件系统，极大地“扩展”了能记录的信息种类和容量上限。

**核心机制：索引节点与目录项**

索引节点（inode）是 Linux 文件系统的核心**数据结构**。每个文件对应一个 inode，里面包含了文件的元数据（如权限、所有者、大小、修改时间等，但**不包含文件名**）和指向实际数据块的指针。

索引节点表（inode table）是一个在文件系统创建（格式化）时就分配的**固定数组**。它的大小决定了该文件系统最多能存储多少个文件。

目录本质上是一种特殊的文件。普通文件的数据块里存的是内容资源，而目录文件的数据块里存的是一行行的“目录项”。每个目录项包含一个文件名和对应的 inode 号码。不管是文件还是目录，都通过索引节点来

**通过 inode 号码在索引节点表中找到对应的 inode，进而得到文件的元数据和数据块位置**。
ext 确立了 Linux 文件系统的基本框架，但存在**碎片化存储**和**文件大小限制**问题。
1. 碎片化存储：数据块分散在磁盘上，通过 inode 的指针链来访问。
2. 文件大小限制：元数据里的文件大小字段是一个 32 位有符号整数，最大只有 2^31 - 1 字节。

> 一个数据块 4KB,里面最多能存 1024 个指针（4 字节），inode 里有 15 个数据块指针：前 12 个是直接指针（指向数据块），第 13 个是单级间接指针（指向一个数据块，里面存 1024 个直接指针），第 14 个是双级间接指针（指向一个数据块，里面存 1024 个单级间接指针），第 15 个是三级间接指针（指向一个数据块，里面存 1024 个双级间接指针）。因此理论上 ext 文件系统最大支持的文件大小为：12*4KB + 1024*4KB + 1024^2*4KB + 1024^3*4KB $\approx$ 4TB。**这种方式导致大文件散落在磁盘上，访问效率较低。**

Linux 出现不久，ext 被 ext2 取代，ext2 把整个硬盘划分成了多个“块组”（Block Group），每个块组都有属于自己的 inode 表和数据块。Linux 会尽量保证文件的 inode 记录及其数据块在同一块组内。本质上是一种牺牲空间换取性能的设计，极大地减少了碎片化问题。

ext2 大幅扩展了 inode 表的记录能力，增加了创建、修改、访问时间戳。同时，突破了 2GB 限制，最大文件支持增加到了 2TB，以满足大型数据库的需求。

但 ext2 的缺陷也很明显：inode表和数据块两者的写入不能确保同时完成（缺乏事务一致性），一旦系统意外断电或崩溃，就会导致文件系统损坏和数据丢失。为了解决这个问题，Linux 引入了 ext3 文件系统（加入了日志功能 Journaling），来保证系统重启后的数据一致性和快速恢复能力。

## 2. 高级文件系统（日志与写时复制）

### 1. 日志功能（Journaling）
基本文件系统是直接在磁盘上读写，而日志功能（Journaling）则是先将修改记录写入日志区，然后写入实际存储设备与索引节点表，最后将日志标记为已完成（commit）。Linux 上有三种常见的日志模式：

1. 数据模式：索引节点和数据都写入日志；丢失风险较低，但性能较差。
2. 有序模式（ext3/ext4）：索引节点写入日志，数据直接写入磁盘；强制要求数据落盘后才允许索引节点在日志中 commit；高效且安全。
3. 回写模式：索引节点写入日志，数据直接写入磁盘；但不保证数据写入和日志 commit 的顺序；性能较好，但存在数据丢失风险。

基本文件系统另一个问题是碎片化存储，一堆指向 4KB 数据块的指针链形成一个大文件。为此 ext4 引入**区段 Extent** 机制，inode 中转为记录一个区段（extent）信息：起始数据块号和连续数据块数量。这样极大地压缩了元数据信息以及访问路径，提升了大文件的访问效率。

> ext4 还引入了块预分配（preallocation）机制，允许应用程序提前申请一段连续的磁盘空间，以避免边下载边分配导致的碎片化问题。

除 ext 系列，Linux 还支持多种其他的日志文件系统，如 Reiser, JFS, XFS 等。

1. ReiserFS：由 Hans Reiser 开发，采用回写模式，性能很快。除此还支持**在线调整文件系统大小**和**尾部压缩**（将小文件填入另一个文件的空白区域）。
2. JFS（Journaled File System）：由 IBM 开发，采用有序模式；它最早采用了区段 (Extent) 机制来减少碎片，虽然后续未能成为主流。
3. XFS：由 SGI 开发，为快速读写大文件而设计，采用回写模式；核心机制是 B+ 树和延迟分配。

### 2. 写时复制（Copy-on-Write）

写时复制（Copy-on-Write，COW）是一种**异地写入**机制。就文件系统而言，COW 算是日志功能的一种平替：修改数据时不直接覆写原始数据，而是先写入新位置，写入完成后将文件指针指向新位置，相当于旧位置是一个只读快照（Snapshot），通过 COW 以零空间代价瞬间生成可写克隆（未修改的共享数据 + 修改的新数据）。

主流的 COW 文件系统有 ZFS 和 Btrfs。

1. ZFS：由 Sun Microsystems 开发；它集成了文件系统和卷管理器的功能，支持数据完整性校验、自动修复、快照和复制等高级特性。
2. Btrfs：由 Oracle 开发；它支持在线调整文件系统大小、内置 RAID 功能、快照和子卷等特性，旨在成为 Linux 的下一代文件系统。

总的来说，ext4 和 XFS 是 Linux 最主流的日志文件系统，兼顾性能与稳定，足以应对绝大多数场景；而 Btrfs 和 ZFS 则凭借“写时复制”（COW）特性，在数据保护和高级功能（如快照、压缩）上更胜一筹。

但在跨平台交互时，NTFS（Windows 的默认文件系统）才是主流选择。现代 Linux 内核已通过 ntfs3 驱动实现了高效的原生支持。NTFS 采用了类似于 ext4 的日志机制，并且支持大文件和长文件名，但其权限管理（ACL）与 Linux 的 POSIX 权限模型不兼容，因此在 Linux 上访问 NTFS 分区时，权限表现可能不如 ext4 等原生文件系统。

## 3. 操作文件系统

Linux 提供了一些命令行工具来管理文件系统，首先在磁盘上创建分区，然后格式化分区，最后挂载文件系统。

1. 在磁盘上创建分区：`fdisk`, `parted`

创建分区最麻烦的地方在与确认设备名称，Linux 采用一种标准格式为硬盘设备命名：老式 IDE 驱动器以 `/dev/hdx` 命名（其中 `x` 是一个字母，从 `a` 开始），现代 SATA/SCSI/USB 驱动器以 `/dev/sdx` 命名。分区则在设备名称后加上数字，如 `/dev/sda1` 表示第一个分区。NVMe (现代 SSD) 驱动器则以 `/dev/nvmeXnY` 命名（其中 `X` 是控制器编号，`Y` 是命名空间编号）。

`/dev/` 下充满了各种虚拟设备（比如 `tty` 是终端，`loop` 是回环设备）。查找块设备的指令一般是 `lsblk` 或 `sudo fdisk -l`，它们会列出所有块设备及其分区信息。用 `df -h` 查看已挂载的文件系统及其使用情况。

`fdisk` 是一个交互式的分区工具，适用于 MBR 分区表；`parted` 支持 GPT 分区表，适用于大于 2TB 的磁盘。

![fdisk](<images/3. shell/fdisk.png>)

> MBR (Master Boot Record) 分区表：自 80 年代起使用，兼容性强。缺点是只支持 4 个主分区槽位（通常其中一个槽位为“扩展分区“，在扩展分区内可以创建无数个“逻辑分区”），单个分区最大只能 2TB。
> GPT (GUID Partition Table) 分区表：现代分区表标准，配合 UEFI BIOS 使用，支持最多 128 个分区，单个分区最大可达 9.4ZB（Zettabyte）。GPT 还在分区表头和尾部都保存了备份，增强了数据安全性。

`parted` 的命令行界面相对更友好，支持交互式操作和脚本化使用。它还支持在线调整分区大小、创建文件系统等功能。

![parted](<images/3. shell/parted.png>)

1. 格式化分区：`mkfs`

格式化分区是根据特定文件系统的规则，在磁盘上写入 Superblock、Inode Table等管理结构。`mkfs` 是一个通用的格式化工具，大多数命令都遵循 `mkfs.[类型]` 的格式（例如 `mkfs.ext4`, `mkfs.xfs`）。

`sudo mkfs.ext4 /dev/sdb1`：创建 ext4 日志文件系统

分区必须“挂载”到目录树的某个节点（挂载点）才能被访问。

```sh
sudo mkdir /mnt/data            # 1. 创建挂载点
sudo mount /dev/sdb1 /mnt/data  # 2. 挂载分区 -t 指定文件系统类型（可选，通常会自动识别）
df -h /mnt/data                 # 3. 验证挂载成功
```

3. 挂载文件系统：`mount` 命令和编辑 `/etc/fstab`

> `mount` 命令是临时挂载，系统重启后会失效。要实现开机自动挂载，需要编辑 `/etc/fstab` 文件。

`/etc/fstab` 文件的每一行定义了一个文件系统的挂载信息，格式如下：

```
<file system> <mount point>   <type>  <options>       <dump>  <pass>
<设备（UUID 或路径）> <挂载点> <文件系统类型> <挂载选项> <是否备份> <fsck 检查顺序>
```
UUID 是一个独特的标识符，可以通过 `sudo blkid /dev/sdb1` 查看，或是直接用设备节点文件路径（如 `/dev/sdb1`）。挂载选项可以是 `defaults`（默认选项），也可以是 `ro`（只读），`noatime`（不更新访问时间）等。

修改后可以用 `sudo mount -a` 来测试 `/etc/fstab` 的配置是否正确，确保没有语法错误或挂载失败。

4. 检查与修复文件系统：`fsck`

fsck 是一个前端工具，用于检查文件系统的一致性，修复因非正常关机（断电、系统崩溃）导致的元数据损坏。**不能对正在运行（已挂载）的文件系统执行**。

先卸载普通分区 `umount /dev/sdb1`，再执行 `sudo fsck /dev/sdb1` 来检查和修复文件系统。fsck 会根据文件系统类型自动调用相应的检查工具（如 `e2fsck` 用于 ext 文件系统）。如果发现问题，fsck 会提示用户是否修复，输入 `y` 确认修复即可。

![fsck](<images/3. shell/fsck.png>)

> 当 NTFS 分区因 Windows 未正常关机（快速启动）或意外拔出而被标记为 “Dirty（脏）” 时，Linux 会出于安全考虑拒绝挂载，并报错 wrong fs type, bad option, ...。这时需要使用 `sudo ntfsfix /dev/sdb1` 来修复 NTFS 分区的状态，或在 Windows 中运行 `chkdsk /f` 来修复文件系统。

## 4. 逻辑卷管理器（LVM）

前文我们说过，Linux 内核通过 VFS 接口层支持多种文件系统，将底层数据以**虚拟目录树**的形式呈现。而逻辑卷管理器（LVM）则是对**物理存储设备**进行抽象和管理的工具，它在硬件层面提供了极其灵活的存储分配能力。

在传统的物理分区中，文件系统的空间被硬盘的物理边界锁死。如果一个分区满了，只能买新硬盘并手动迁移数据。LVM 则打破了这种限制，它将多个物理硬盘抽象成一个巨大的“存储池”，再从池子里自由划分空间。这样就可以动态调整分区大小，甚至在运行时扩展或缩小文件系统。

LVM 的核心架构分为三层：

- 物理卷（PV）：底层的物理存储分区，如 `/dev/sdb1`。
  - 通过 `fdisk /dev/sdb` 进入分区工具，`n` 新建分区，`t` 修改分区类型为 `8e`（Linux LVM），`w` 写入分区表。
  - 使用 `pvcreate /dev/sdb1` 将分区初始化为物理卷。
- 卷组（VG）：由一个或多个物理卷组成的"存储池"，在操作系统眼里就是一个可以动态扩容的大硬盘。
  - 使用 `vgcreate myvg /dev/sdb1` 创建一个名为 `myvg` 的卷组。
- 逻辑卷（LV）：从卷组中划分出来的逻辑分区，可以像普通分区一样格式化和挂载。
  - 使用 `lvcreate -L 10G -n mylv myvg` 从 `myvg` 卷组中创建一个名为 `mylv` 的逻辑卷，大小为 10GB。
  - 格式化：`mkfs.ext4 /dev/myvg/mylv`
  - 挂载：`mount /dev/myvg/mylv /mnt/data`

> 如果需要扩展逻辑卷的大小，可以先使用 `lvextend -L +5G /dev/myvg/mylv` 将逻辑卷 LV 扩大 5GB，然后使用 `resize2fs /dev/myvg/mylv` 来调整文件系统大小，使其利用新增的空间。
> LVM 赋予了“容器”动态调整的能力，但“内容物（文件系统）”是否支持在线（Live/Online）调整，取决于文件系统自身。

![extend](<images/3. shell/extend.png>)

Linux LVM 有两个主要版本：1998 年发布的 LVM1（基础版）和 2004 年发布的 LVM2。LVM2 是对内核存储架构的重写，除了支持海量容量，其核心价值在于提供了以下企业级特性：

- 快照（Snapshot）：捕捉 LV 在某一特定时刻的“状态瞬间”。也是 COW 写时复制机制（只记录修改前的数据块）。
  - `sudo lvcreate -L 2G -s -n mylv_snap /dev/myvg/mylv` 创建一个名为 `mylv_snap` 的快照，大小为 2GB。
- 条带化（Striping）：类似于 RAID 0，将数据块分散写入多个物理卷，追求极致读写性能。
  - `sudo lvcreate -L 20G -i 2 -I 64 -n lv_stripe myvg`
- 镜像（Mirroring）：类似于 RAID 1，实时同步两份完全相同的数据，保障高可用性。
  - `sudo lvcreate -L 10G -m 1 -n lv_mirror myvg`。

LVM2 快照采用的是 “同地写入” 机制：当你修改原始数据时，LVM2 会先将“旧数据”拷贝到快照缓冲空间，然后再让新数据覆盖原始位置。对比我们之前介绍的 COW 文件系统的“异地写入”机制，其采用的则是修改时不覆盖旧数据而是直接写新位置。

LMV2 快照的痛点就是每次修改数据都会触发“一读二写”：读取旧数据 -> 写入快照区 -> 写入原始卷。这会造成显著的 I/O 延迟。因此，快照只适合短期保存，不建议作为长期备份手段。

快照驱动器（snapshot driver）是一个特殊的设备映射器（device mapper），它会在内核中维护一个快照元数据结构来跟踪原始卷和快照卷之间的关系。当应用程序访问快照卷时，内核会根据访问的数据块是否已修改来决定是从原始卷读取数据还是从快照缓冲区读取数据。因此，快照挺适合当一个沙盒环境，哪怕执行 `rm -rf /` 也不会对原始数据造成任何损害；也可以作为一个临时的回滚点。

场景一：将 LV 快照作为"沙盒实验区"：
```sh
sudo lvcreate -L 2G -s -n mylv_snap /dev/myvg/mylv  # 创建快照
sudo mount /dev/myvg/mylv_snap /mnt/snapshot  # 挂载快照
# 在 /mnt/snapshot 中进行测试，修改数据不会影响原始卷
sudo umount /mnt/snapshot  # 卸载快照
sudo lvremove /dev/myvg/mylv_snap  # 删除快照
```

场景二：将 LV 快照作为“存档回滚点”
```sh
sudo lvcreate -L 2G -s -n mylv_backup /dev/myvg/mylv  # 创建快照
sudo lvconvert --merge /dev/myvg/mylv_backup  # 合并快照，如果 LV 正在被使用，合并会在下次挂载时生效
```

快照只是一个逻辑上的“时间点”，如果原始卷发生物理损坏，快照也会受到影响。对于长期备份，建议使用镜像（Mirroring）或外部备份工具（如 rsync、tar、Bacula 等）来实现数据的冗余和安全。镜像是一种“全量复制”，但在日常使用阶段会有双写负担。
